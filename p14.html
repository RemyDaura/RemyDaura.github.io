DOSSIER N°14 · PROJET PERSONNEL

Pipeline automatisé des prix des carburants

Construire de bout en bout un pipeline de données qui tourne seul chaque matin, de l'API publique jusqu'au tableau de bord, avec des tests qui arrêtent les données douteuses avant qu'elles n'arrivent à l'écran.

Contexte Projet personnel, spécialisation data engineering Outils Python, BigQuery, dbt, GitHub Actions, Docker, Data Studio Statut En production depuis novembre 2026

Contexte

Après la formation Data Analyst, je me spécialise en data engineering. Mes projets précédents partaient d'un fichier déjà préparé ; celui-ci part d'une source vivante, qui change toutes les dix minutes, et doit produire chaque jour un résultat fiable sans aucune intervention de ma part.

La source : le flux public des prix des carburants publié par la DGCCRF, qui couvre près de 9 800 stations-service en France.

Besoin

Le flux est un instantané : chaque mise à jour écrase la précédente, donc aucun historique n'existe sans le construire. Les données sont aussi imparfaites : stations qui ne mettent plus leurs prix à jour, erreurs de saisie, champs manquants.

Objectif : un historique quotidien fiable, testé à chaque étape, qui réponde à trois questions. Comment évolue le prix de chaque carburant, en France et dans les Bouches-du-Rhône ? Quels départements sont les plus chers ? Quelles sont les stations les moins chères autour de Marseille ?

Démarche

Chaque matin, GitHub Actions enchaîne les étapes suivantes, et s'arrête dès qu'un test bloquant échoue :

  • Ingestion Python : téléchargement de toutes les stations, sélection de 24 colonnes, écriture d'un fichier Parquet, avec des tests pytest qui arrêtent tout si la source supprime une colonne.
  • Chargement BigQuery : ajout à une table brute partitionnée par jour, qui garde tout et n'est jamais modifiée.
  • Transformation dbt en trois couches : nettoyage et dédoublonnage, étiquetage de chaque prix (récent ou périmé, normal ou suspect), puis tables finales pour le tableau de bord.
  • Restitution dans un tableau de bord Data Studio public, dont chaque chiffre a été vérifié en SQL.

L'ingestion est aussi conteneurisée avec Docker, pour tourner à l'identique sur n'importe quelle machine. Aucune clé n'est stockée dans le code : le pipeline utilise un compte de service limité à BigQuery, rangé dans les secrets de GitHub.

Résultats

9 800stations chargées et transformées chaque matin, sans intervention
15tests dbt à chaque run, en plus des tests Python
17prix suspects détectés automatiquement dès le premier relevé

Les tests ont révélé des problèmes que je n'aurais pas vus à l'œil : 4 stations sans département ni ville dans la source, dont le département est désormais retrouvé à partir du code postal, et une règle de fraîcheur trop stricte. Avec un seuil de 7 jours, 16 % des prix étaient écartés ; l'analyse de la distribution m'a fait passer à 30 jours, qui n'écarte plus que 5,6 % des prix, ceux qui n'ont pas bougé depuis plus d'un mois.

Côté tableau de bord, les moyennes nationales sont calculées dans dbt à partir des sommes exactes, pondérées par le nombre de stations : ni moyenne de moyennes départementales, ni calcul sur des valeurs déjà arrondies.

Limites et pistes

  • BigQuery tourne en mode bac à sable gratuit : l'historique est limité à environ 60 jours, et les tables finales sont recréées à chaque run plutôt que mises à jour de façon incrémentale.
  • Les données disponibles couvrent 96 départements métropolitains.
  • Prochaines étapes : authentification sans aucune clé (Workload Identity Federation), exécution sur Cloud Run, puis un assistant qui répond en langage naturel aux questions sur les prix.
